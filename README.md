# 📜 PiC: Personal Information Center
# Project Manifesto & Framework V2 (English)

## 🎯 Vision
PiC teaches users how to connect to their
Personal Information Center for self-healing.
The body is the ultimate database,
containing all the answers regarding
any illness, condition, or symptom.
All the answers already exist within you;
the PiC app provides the tools and
methodology to connect to this information
and use it to lead your own healing process.

---

## 🛠️ Core Principles

### 1. Ownership & Responsibility
The system is a hub for learning and
action that empowers users to take
full responsibility for their health.
The user acts as the "Event Manager"
of their healing process, managing it
based on a deep understanding of their needs.

### 2. The Body as the Database
The system serves as an intelligent
interface that enables the user to
access the existing answers within them
and tap into their inherent internal knowledge.
We work alongside the Center,
organizing the insights gained to
facilitate communication with the
internal knowledge base.

### 3. Flexible Journey Gate
"The Empty Vessel" (הכלי הריק / mental
decluttering) is a recommended gate:
free, unstructured writing to clear
mental space—not only listing symptoms,
but also spontaneous notes (e.g. how
you feel today, insights about a
Symptom Group). Users may skip it and
go directly to any other step when
that fits their immediate needs.

### 4. Parallel Symptom Groups (הקשר)
Users manage multiple **Symptom Groups**
(קבוצת סימפטומים / מכלי הסימפטומים /
הקשר) and active courses in parallel.
Each group **is** one persistent
**Work Session** (סשן עבודה): full
logbook, documentation on any object
in the group, ratings, and treatment
history. To form groups: list symptoms,
then a **joint treatment muscle test**—
keep together when the test allows;
split into separate groups only when
it does not. Distinct groups stay
separate so different healing processes
do not mix.

### 5. Atomic Focus
One muscle-test question and one Player
step at a time (one screen, one action)
to reduce cognitive overload. During an
**Inquiry Session**, keep **one focus** at
a time: **symptom-led** work on one
Symptom Group, **course-led** work when a
**course as treatment** is chosen, or a
**timeline-first** visit (e.g. a technique
or treatment run without a required group
row)—see `decisions.md` **DEC-003** and
**DEC-004**. Users may **switch** by
**starting a new Inquiry Session** whenever
they choose. ADHD-friendly pacing—not a
separate container type (see `CONTEXT.md`).

### 6. Offline Resilience
The app is designed to support
"Flight Mode" to ensure therapy
continuity without distractions,
radiation, or dependency on
network connectivity.

## 💎 Features & Ecosystem

### 1. The Gateway (Academy)
A free introductory course teaching
the method's principles, muscle testing,
and the art of inquiry.
Learning the core method is always
free and open to all.
However, saving data, tracking history,
and persistent session memory require
a paid subscription.

### 2. The Inquiry Engine & Logic (NEMAR)
A dynamic interactive interface linking
user intent with the body's information
using binary (Yes/No) and scale (0-10)
logic, based on the NEMAR principles
(Right, Accurate, Desirable).

* **The Inquiry Flow:**
    1. **Safety Check:** Before starting,
       verify there is no "Self-Sabotage"
       pattern blocking the process.
    2. **The Left Path (Root Cause):**
       Ask: *"Is it NEMAR to diagnose
       a Root Cause?"*. If yes, identify
       the type (Physical/Emotional/
       Energetic/Conscious) and locate
       it in the **Causes Table**.
    3. **The Right Path (Treatment):**
       If no, navigate to the right path
       to identify the precise intervention
       from the **Treatments Table**.
    4. **Execution Instructions:**
       Diagnose the specific technique,
       provider, duration, frequency,
       and repetition.

* **Inquiry Session (סשן):** One sitting with
  **one chosen focus**—symptom-led on a
  Symptom Group, course-led when a **course
  as treatment** is chosen, or **timeline-first**
  technique/treatment work. Steps—Empty
  Vessel, safety check, NEMAR inquiry,
  treatment player, journal—may be
  **entered and run in any order** where the
  path applies. **Recommended** order: Empty
  Vessel → safety → NEMAR → player → journal.
  New sessions may start whenever the user
  chooses (any focus, any entry point).

### 3. Dynamic Assessment, Polarity Ratings & Smart-Linking
* **Symptom Refinement:** On **symptom–group
  inquiry paths**, users can rephrase or
  refine symptoms when that focus is active,
  to keep language aligned with the body.
* **Polarity & Directional Flexibility:** Each symptom has a **polarity** (Positive or Negative) reflecting its current
  state's valence (e.g., "Back Pain" [Negative] → "Back Strength" [Positive]). The Event Manager may **flip polarity** during
  any rating update, supporting the healing narrative where symptoms evolve (**DEC-009**).
* **Blind (re-)rating (symptoms only):** On
  those paths, blind rating refresh may be
  offered with the **previous polarity and/or
  intensity hidden by default** (**DEC-011**);
  the EM can easily request to see one or both
  prior dimensions via simple toggle controls
  (**DEC-011**).
  The Event Manager may
  also start **ad-hoc** re-rating anytime. Not
  implied for pure course, library, or
  timeline-only work unless a symptom is
  intentionally in scope.
* **Atomic Focus in Rating:** Only one symptom
  rated at a time; a symptom belongs to only
  one Symptom Group, ensuring focused Work
  Sessions (**DEC-009**).
* **Smart-Link Suggestion (Feedback Loop):**
  When a timeline execution is linked to a
  Symptom Group or symptom, the system proactively suggests rating those associated
  symptoms, closing the feedback loop between
  technique and "The Center" (**DEC-008**, **DEC-009**).
* **Bias Prevention:** During blind symptom
  input, the system **hides** the prior polarity
  and/or intensity unless the Event Manager requests override.
* **Independent Intensity:** Each symptom tracks **Intensity** (0–10 magnitude) **independently** of Polarity (**DEC-010**).
  This enables pure growth measurement: a symptom can shift from "Back Pain" 8/10 Negative to "Back Strength" 2/10 Positive—the
  magnitude story persists and reveals healing regardless of how the EM reframes the symptom.

### 4. The Networked Reflective Journal
A chronological archive for thoughts and
insights—aligned with the **chronological
timeline** that anchors sessions and
executions unless the Event Manager links
them elsewhere (`decisions.md` **DEC-004**).
Entries can be retroactively "Smart-Linked"
to multiple symptoms, treatments, or courses
simultaneously, or exist independently,
breaking traditional rigid hierarchies.
Every Inquiry Session may conclude with an
invitation to document insights or
personal tasks in the Reflective Journal.

### 5. Adaptive Player & Integration State
A step-by-step player for protocols.
If a session or treatment is incomplete
or has not reached full success,
it is never categorized as "Failed"
or "Error". Instead, it is marked as
**"Integrating"** or **"In Progress"**.

* **Reasons for Integration:** 
    1. *Repetition:* The body requires
       more cycles of the treatment.
    2. *Pending Tasks:* The user committed
       to specific actions/commitments
       during the session that are
       yet to be completed.
    3. *Permeation:* The process needs
       time to "sink in" or "permeate"
       into the physical or energetic body.

* **Personal Treatment Library use_count:**
  Rises **automatically** only when the Event
  Manager completes the Player through
  **Finish** (סיום) after **required** steps; an
  **optional** closing **yes/no** muscle-test
  (*did it end successfully?*) may appear per
  protocol. **Integrating** mid-exits do **not**
  auto-increment. **Manual +1** is always
  available for honest off-Player logging
  (`decisions.md` **DEC-006**).

## 🏗️ Technical Architecture
* **Stack:** Flutter (Frontend) &
  Supabase (Backend/PostgreSQL with RLS).
* **Modular Web-to-Mobile:** Full separation
  between the logic engine and content layer,
  allowing a seamless transition from a Web App
  to a Mobile App (Android/iOS) with
  a shared codebase.
* **Data Sovereignty:** Users have the
  absolute right to permanently delete
  all personal data from the app's
  databases at any time.
* **AI Ready:** Structured data infrastructure
  optimized for future **AI Agent** integration
  to analyze personal trends within the journal.
* **Git Standards:** All commit messages
  must be written in simple, human-readable
  English for non-programmers.
* **Line length:** No source or doc line may exceed
  130 characters. Staged files are checked on commit
  (`scripts/check-max-line-length.py`). One-time setup:
  `git config core.hooksPath .githooks`.

## 👥 Appendix A: PiC Shared Vocabulary
To ensure we are aligned, we use specific
terms that carry unique philosophical and
therapeutic meanings in PiC. Do not replace
them with generic tech jargon:

* **The Center:** Refers to the Personal
  Information Center—the user's inner
  database (the body). We do not "calculate"
  or "predict" answers; we *retrieve* them
  from the Center via muscle testing.
* **Event Manager:** The role of the user.
  The user is not a passive "patient" or
  just an "end-user"; they are the active
  director and event manager of their
  own healing journey.
* **Integrating:** A state where a treatment
  or session is ongoing, rather than completed.
  We never use words like "Failed", "Error",
  or "Incomplete". If a process needs time,
  repetition, or pending tasks, it is
  simply *Integrating*.
* **Smart-Linking:** The non-linear relationship
  between journal entries, timeline events,
  and treatment or technique executions. The
  Event Manager links **at any time** (during
  or after a session), can link one event to
  **multiple groups/courses** simultaneously,
  and can **unlink anytime** with light
  confirmation. Linking and unlinking are
  logged as timeline events (**DEC-008**);
  the app does not silently default a parent.
* **Chronological timeline:** The ordered spine
  of healing activity; executions may stand
  alone until Smart-Linked (`decisions.md`
  **DEC-004**).
* **Personal Treatment Library:** The Event
  Manager’s toolbox: **one logical card** per
  technique/treatment with **provenance**,
  **use count only** on the card (v1), and
  **opt-in named variants** (`decisions.md`
  **DEC-005**). **Auto +1** on Player **Finish**
  (סיום) after **required** steps; **optional**
  closing **yes/no** muscle-test (*ended
  successfully?*) per protocol; **manual +1** anytime
  (`decisions.md` **DEC-006**); keep the count
  **quiet**—reflection, not pressure. Fed from
  courses, the Treatments Table, or self-invented
  work (`CONTEXT.md`).
* **Symptom Group (הקשר):** Symptoms treated
  together per a joint muscle test; equals
  מכלי הסימפטומים and one Work Session.
  _Avoid:_ Symptom Bucket as a separate type.
* **Work Session (סשן עבודה):** The continuous
  saved thread for one Symptom Group—not
  a parent of multiple groups.
* **Inquiry Session (סשן):** One visit with one
  chosen **focus**—symptom-led on a group,
  course-led for a **course as treatment**, or
  timeline-first technique/treatment work;
  flexible step order (see Principles 3–5).
* **Empty Vessel (הכלי הריק):** Optional free
  writing gate; not only a symptom list.

Full glossary: `CONTEXT.md`. Architecture
agreements: `decisions.md`.

## 🤝 Appendix B: Co-Architect Workflow

### Our Partnership
You are our collaborative Lead System
Architect, working hand-in-hand with
Yossef-Tal and Sigal. Our goal is to
think together, consult with one another,
and translate the PiC Manifesto into
a clean, modular technical reality.

### The Iterative Journey (OpenSpec Standard)
We design this application together,
step-by-step, using the OpenSpec standard.
Before moving from one phase to the next,
we will review the draft together, share
feedback, and ensure we have reached
a mutual agreement:
1. **Proposal:** We map out the feature's
   logic and scope in a joint `proposal.md`.
2. **Design:** We refine the technical
   design and shape the data structures.
3. **Tasks:** We break down the design
   into atomic, manageable tasks.

### One Step at a Time
During the implementation phase, we will
focus on **only one task at a time**.
We will review the output together,
consult on how to improve it, and
iterate until we both agree it is rock-solid.
We will move to the next task only
after we’ve aligned on the current one.

### Shared Definition of Quality
Every solution we design must incorporate
both **Quality Assurance (QA) tests**
(for stability) and **Logical Verification**
(to ensure the app seamlessly reflects
the NEMAR rules and therapeutic flows).

### Living Documentation
Our documentation is alive. During our
brainstorming sessions, whenever we reach
a mutual agreement or change a logical
nuance, your first task is to document it.
You will create or update a `decisions.md`
file (Architectural Decision Record)
to capture the "Why" and "How" before
writing any feature specification.

### Context Management & Session Refresh
If you ever feel that the conversation
history is becoming too heavy, degrading
in quality, or approaching its token limits,
proactively let us know. Pause the process
and ask us to start a fresh conversation.
Before we switch, provide a concise,
structured summary of our current state,
active tasks, and recent `decisions.md`
updates so we can seamlessly carry them
over to the new session.

### Brainstorming & Open Dialogue
If a requirement feels ambiguous, or if
you feel we need to dive deeper into the
therapeutic nuance (like "The Empty Vessel"
or "Integration State"), let's pause and
brainstorm. Reach out to Yossef-Tal or
Sigal so we can talk it through and
find the best path together.

## 🛠️ עקרונות הליבה

### 1. אחריות ובעלות
המערכת היא מרכז למידה ופעולה
המעניק למשתמש את הכלים
להוביל את בריאותו באופן עצמאי.
המשתמש הוא "מנהל האירוע"
של תהליך הריפוי שלו,
הפועל מתוך הבנה עמוקה של צרכיו.

### 2. הגוף כמאגר המידע
המערכת משמשת כממשק חכם
המאפשר למשתמש לגשת לתשובות
הקיימות בתוכו ולמצות את
הידע הפנימי הטמון בו.
המשתמש פועל לצד מאגר המידע,
והאפליקציה מארגנת את הנתונים
שהושגו כדי לסייע בתקשורת
עם מאגר המידע הפנימי.

### 3. שער כניסה גמיש
"הכלי הריק" (פינוי מנטלי) הוא שער מומלץ:
כתיבה חופשית לניקוי מחשבתי — לא רק
רשימת תסמינים, אלא גם תיעוד ספונטני
(למשל איך אני מרגיש היום, תובנה על
קבוצת הסימפטומים). ניתן לדלג ולעבור
ישירות לכל שלב אחר לפי הצורך.

### 4. קבוצות סימפטומים במקביל (הקשר)
המשתמש מנהל מספר **קבוצות סימפטומים**
(קבוצה / מכלי הסימפטומים / **הקשר**)
וקורסים פעילים במקביל. כל קבוצה **היא**
**סשן עבודה** רציף: יומן מלא, תיעוד על
כל אובייקט בקבוצה, דירוגים והיסטוריית
טיפולים. יצירת קבוצות: רשימת תסמינים,
ואז **מבחן טיפול משותף** — יחד כשהמבחן
מאפשר; פיצול לקבוצות נפרדות רק כשלא.
קבוצות נפרדות שומרות על הפרדה בין
תהליכי ריפוי שונים.

### 5. מיקוד אטומי
שאלת נמ"ר אחת וצעד נגן אחד בכל פעם
(מסך אחד, פעולה אחת). ב**סשן** (שאילתה)
עובדים על **מוקד אחד** בכל פעם: **מוביל-תסמין**
על **קבוצת סימפטומים** אחת, **מוביל-קורס**
כש**קורס כטיפול** נבחר, או **מוביל-ציר זמן**
(למשל הרצת טכניקה/טיפול בלי שורת קבוצה
חובה)—ראו `decisions.md` **DEC-003**–**DEC-004**.
ניתן **להחליף מוקד** ב**פתיחת סשן חדש**
בכל עת. מותאם ל-ADHD — לא סוג מיכל נפרד
(ראו `CONTEXT.md`).

### 6. חוסן במצב מנותק
תמיכה מלאה ב"מצב טיסה"
לעבודה נקייה מהסחות דעת,
ללד קרינה ובכל מקום,
ללא תלות בחיבור לרשת.

## 💎 רכיבי המערכת

### 1. השער (האקדמיה)
קורס מבוא חינמי המלמד את
עקרונות השיטה, ביצוע מבחן שרירים
וטכניקת שאילת שאלות.
הגישה ללימוד השיטה חופשית לכולם,
אך היכולת לשמור נתונים, לתעד
ולנהל היסטוריית מעקב דורשת
מנוי בתשלום.

### 2. מנוע השאילתות ולוגיקת נמ"ר
ממשק אינטראקטיבי המתווך בין
כוונת המשתמש למידע בגוף,
מבוסס על לוגיקה בינארית (כן/לא)
ומדדי ערך (1-10) על פי עקרונות
הנמ"ר (נכון, מדויק, רצוי).

* **סדר השאילתות המובנה:**
    1. **בדיקת חסמים:** לפני התחלת
       התהליך, יש לוודא שאין דפוס
       של "חבלה עצמית" החוסם ריפוי.
    2. **הנתיב השמאלי (אבחון גורם):**
       השאלה הראשונה: *"האם נמ"ר
       לאבחן גורם?"*. אם כן, מאבחנים
       את סוג הגורם ומאתרים אותו
       ב**טבלת הגורמים**.
    3. **הנתיב הימני (אבחון טיפול):**
       אם לא, עוברים לנתיב הימני
       לזיהוי הטיפול המדויק ביותר
       מתוך **טבלת הטיפולים**.
    4. **הנחיות ביצוע:** הגדרת הטכניקה,
       הגורם המטפל, המשך, התדירות
       והחזרתיות הנדרשים.

* **סשן (שאילתה):** ישיבה אחת עם **מוקד נבחר**—עבודה **מובילת-תסמין** על **קבוצת
  סימפטומים**, **מובילת-קורס** כש**קורס כטיפול** נבחר, או **מובילת-ציר זמן** לטכניקה/טיפול.
  שלבים — הכלי הריק, בדיקת חסמים, נמ"ר, נגן טיפול, יומן —
  ניתן **להיכנס ולבצע בכל סדר** כשהנתיב רלוונטי.
  **מומלץ:** הכלי הריק → חסמים → נמ"ר →
  נגן → יומן. ניתן לפתוח סשן חדש בכל עת (כל מוקד, כל נקודת כניסה).

### 3. הערכה דינמית, דירוג קוטביות וקישור חכם
* **דיוק סימפטומים:** ב**נתיבי שאילתה מובילי-קבוצה**,
  ניתן לדייק או לשנות ניסוח תסמין כשהמוקד
  הפעיל רלוונטי.
* **קוטביות ו"גמישות כיוון":** לכל סימפטום יש **קוטביות** (חיובית או שלילית)
  המשקפת את ערך המצב הנוכחי (למשל, "כאב גב" [שלילי] → "חוסן גב" [חיובי]).
  מנהל האירוע יכול **לשנות קוטביות** בכל עדכון דירוג, ואף לשנות שם התסמין
  לשיקוף הנוסחה החדשה (**DEC-009**).
* **דירוג עיוור (לתסמין בלבד):** בנתיבים
  אלה ניתן להציע רענון עיוור עם **הסתרת הקוטביות
  ו/או העוצמה הקודמות כברירת מחדל** (**DEC-011**); מנהל האירוע יכול בקלות
  לבקש לראות אחד או שניים מהממדים הקודמים דרך כפתור toggle פשוט
  (**DEC-011**); מנהל האירוע יכול גם **אד-הוק** לדרג
  מחדש מתי שירצה. לא מנוהל אוטומטית במסלול
  קורס-בלבד, ציר-זמן בלבד או ספרייה בלבד אלא אם
  תסמין במפורש בתוך ההיקף.
* **מיקוד אטומי בדירוג:** המערכת מדרגת תסמין אחד
  בכל פעם; תסמין שייך לקבוצה אחת בלבד כל רגע,
  מה שמבטיח סשן עבודה ממוקד (**DEC-009**).
* **הצעת קישור לסגירת מעגל משוב:** כאשר ביצוע
  טכניקה מקושר לקבוצת סימפטומים או תסמין ספציפי,
  המערכת מציעה לדרג את הסימפטומים המשויכים,
  וסוגרת את מעגל המשוב בין הביצוע ל"המרכז" (**DEC-008**, **DEC-009**).
* **מאפיין דירוג:** כל סימפטום עוקב אחר מאפיין אחר - **עוצמה** (0–10) או **קוטביות** (**DEC-010**).
  זה מאפשר מדידת צמיחה טהורה: תסמין יכול להעבור מ"כאב גב" 8/10 שלילי ל"חוסן גב" 2/10 חיובי—
  מעקב אחר מאפיינים אלו משקף (בצורה מסויימת) את השינוי המתרחש לאורך תהליך הריפוי, בנוסף על הרצף הטיפולי המתועד
* **מניעת הטיות:** בזמן הזנת דירוג עיוור לתסמין,
  המערכת **מסתירה** את הקוטביות ו/או העוצמה הקודמות
  אלא אם מנהל האירוע מבקש במפורש לראותם.

### 4. יומן המסע הרשתי
ארכיון כרונולוגי חכם לתיעוד
ספונטני או מובנה—בהתאמה ל**ציר הזמן
הכרונולוגי** שעוגן סשנים וביצועים אלא
אם מנהל האירוע מקשר אחרת (`decisions.md`
**DEC-004**). ניתן לקשר
תיעוד ל**מספר אובייקטים במקביל**
(תסמינים, טיפולים או קורסים),
לבצע קישור רטרואקטיבי או לנתק
שיוכים בכל עת. כל **סשן** (שאילתה) יכול
להסתיים בהצעה להוסיף תיעוד ותובנות ליומן.

### 5. נגן טיפול ומצב הטמעה
נגן המלווה את הפרוטוקולים
צעד-אחר-צעד. תהליך שטרם הושלם
או לא הגיע להצלחה מלאה לעולם
לא יוגדר כ"כישלון" או "שגיאה".
הוא יוגדר כטיפול **בשלבי הטמעה**
או **בתהליך**.

* **סיבות למצב הטמעה:**
    1. הצורך בחזרתיות של הטיפול.
    2. משימות ומחויבויות פתוחות
       שהמשתמש לקח על עצמו במהלך
       הסשן וטרם הושלמו.
    3. צורך של הגוף בזמן נוסף
       כדי שהטיפול "יחלחל" וישקע.

* **מונה בספרייה האישית:** עלייה **אוטומטית**
  רק אחרי **סיום** הנגן לאחר כל השלבים
  **הנדרשים**; אפשר **מבחן שרירים כן/לא
  אופציונלי** בסוף (*האם הסתיים בהצלחה?*)
  לפי פרוטוקול. יציאה באמצע במצב **בהטמעה**
  **לא** מעלה את המונה אוטומטית; **+1 ידני**
  זמין תמיד (`decisions.md` **DEC-006**).

## 👥 נספח א': שפה משותפת ומילון מונחים
כדי להבטיח התאמה מלאה, נשתמש
במושגים ספציפיים הנושאים משמעות
פילוסופית וטיפולית ייחודית ב-PiC:

* **המרכז (The Center):** מתייחס למרכז
  המידע האישי – מאגר המידע הפנימי
  של המשתמש (הגוף). המערכת אינה
  "מחשבת" או "מנבאת" תשובות, אלא
  *שולפת* אותן באמצעות מבחן שרירים.
* **מנהל אירוע (Event Manager):**
  תפקידו של המשתמש. המשתמש אינו
  "מטופל" פסיבי או "משתמש קצה";
  הוא המנהל הפעיל ומוביל אירוע
  הריפוי של עצמו.
* **בהטמעה (Integrating):** מצב שבו
  טיפול או סשן נמצאים בעיצומו וטרם
  הושלמו. לעולם אין להשתמש במילים
  כמו "נכשל", "שגיאה" או "לא הושלם".
  אם תהליך דורש זמן, חזרתיות או
  משימות פתוחות, הוא פשוט *בהטמעה*.
* **קישור רשתי (Smart-Linking):**
  קשר לא-ליניארי בין רשומות יומן, אירועי
  ציר זמן, וביצועי טיפול או טכניקה.
  מנהל האירוע מקשר **בכל עת** (במהלך או
  אחרי סשן), יכול **לקשר אירוע אחד למספר
  קבוצות/קורסים** במקביל, ויכול **לנתק בכל עת**
  עם אישור קל. קישור וניתוק מתועדים כאירועי
  ציר זמן (**DEC-008**), ללא ברירת מחדל שקטה.
* **ציר זמן כרונולוגי:** עמוד השדרה המסודר
  לפעילות ריפוי; ביצועים עומדים לבד עד
  קישור חכם (`decisions.md` **DEC-004**).
* **ספריית טיפולים אישית:** ארגז הכלים
  של מנהל האירוע: **כרטיס לוגי אחד** לכל
  טכניקה/טיפול עם **מקורות**, **מונה שימושים
  בלבד** (ב-v1), ו**וריאנטים בשם** לבחירה
  כשהשינוי מהותי (`decisions.md` **DEC-005**).
  **עדכון אוטומטי +1** ב-**סיום** נגן אחרי
  שלבים נדרשים; **מבחן שרירים אופציונלי**
  בסוף (*האם הסתיים בהצלחה?*) לפי פרוטוקול;
  **עדכון ידני +1** בכל עת
  (`decisions.md` **DEC-006**); המונה **משני**
  ולא מלחיץ. מזינים מקורס, טבלת טיפולים,
  או עבודה עצמית (`CONTEXT.md`).
* **קבוצת סימפטומים (הקשר):** תסמינים
  לטיפול משותף לפי מבחן משותף; שווה
  למכלי הסימפטומים ולסשן עבודה אחד.
* **סשן עבודה:** המשכיות השמורה של קבוצה
  אחת — לא מיכל אב של כמה קבוצות.
* **סשן (שאילתה):** ביקור עם **מוקד נבחר**—מוביל-תסמין על קבוצה, מוביל-קורס ל**קורס כטיפול**, או מוביל-ציר זמן לטכניקה/טיפול;
  סדר שלבים גמיש (עקרונות 3–5).
* **הכלי הריק:** שער כתיבה חופשית; לא רק
  רשימת תסמינים.

מילון מלא: `CONTEXT.md`. החלטות ארכיטקטורה:
`decisions.md`.

## 🤝 נספח ב': עבודה משותפת ב-OpenSpec

### השותפות שלנו
אתה שותף להובלת הארכיטקטורה של
הפרויקט, ויחד עם יוסף-טל וסיגל
נתרגם את המניפסט של PiC למציאות
טכנולוגית נקייה ומודולרית.
המטרה שלנו היא לחשוב ולהתייעץ
יחד לאורך כל הדרך.

### מסע משותף (תקן OpenSpec)
אנחנו מתכננים את האפליקציה הזו
יחד, שלב אחר שלב, לפי תקן OpenSpec.
לפני שנעבור משלב לשלב, נבחן את
הטיוטה יחד, נחליף רשמים ונוודא
שהגענו להסכמה מלאה:
1. **הצעה (Proposal):** נמפה יחד את
   הלוגיקה והיקף הפיצ'ר ב-`proposal.md`.
2. **עיצוב (Design):** נדייק יחד את
   העיצוב הטכני ומבני הנתונים.
3. **משימות (Tasks):** נפרק את התכנון
   המוסכם למשימות פיתוח קטנות.

### מתקדמים רק אחרי שמסכימים
בשלב הביצוע, נתמקד בכל פעם
ב**משימה אחת בלבד**.
נתייעץ לגבי התוצר, נשפר אותו יחד
באיטרציות, ונתקדם למשימה הבאה
רק לאחר שהגענו לעמק השווה והסכמנו
שהתוצאה הנוכחית מעולה.

### איכות ולוגיקה משולבות
כל פתרון שנתכנן יכלול גם
**בדיקות איכות (QA)** ליציבות,
וגם **בדיקות לוגיות** כדי לוודא
שהיישום זורם בצורה מושלמת עם
חוקי הנמ"ר ועצי ההחלטות.

### תיעוד דינמי תוך כדי תנועה
התיעוד שלנו חי ונושם. במהלך שיחות
החשיבה שלנו, בכל פעם שנגיע להסכמה
או נשנה ניואנס לוגי, המשימה הראשונה
שלך תהיה לתעד זאת.
נפתח או נעדכן יחד קובץ `decisions.md`
(Architectural Decision Record) שיתעד
את מהות ההחלטה וההיגיון מאחוריה,
עוד לפני שניגש לכתוב אפיון טכני.

### ניהול קונטקסט ורענון שיחה
אם בשלב כלשהו תרגיש שהיסטוריית
השיחה נהיית כבדה מדי, שאיכות התשובות
עלולה לרדת, או שאנחנו מתקרבים למגבלת
הזיכרון (Token limits), תציף את זה
בצורה יזומה.
עצור את התהליך ובקש מאיתנו לעבור
לשיחה חדשה. לפני המעבר, ספק לנו
סיכום תמציתי ומאורגן של המצב הנוכחי,
המשימות הפתוחות והעדכונים האחרונים
ב-`decisions.md`, כדי שנוכל להעביר
את המידע איתנו חלק לשיחה הבאה.

### פותחים הכל לשיחה
אם משהו באפיון מרגיש לא ברור,
או אם יש צורך לדייק את הניואנס
הטיפולי (כמו "הכלי הריק" או "שלב
ההטמעה"), נעצור לרגע ונחשוב יחד.
תמיד אפשר לפנות ליוסף-טל או לסיגל
כדי שנוכל להתייעץ ולמצוא את
הדרך הנכונה ביותר.
